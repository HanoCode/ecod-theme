设计规格

插件定位、信息架构、数据模型与实现约定

设计稿 v1 · 2026-10-31
前提假设：这里的「主题授权」指本站这份主题的授权状态——授权码、绑定域名、到期时间、模块解锁、版本更新通道，由主题作者签发、插件负责校验与续期。若你要的是「把主题卖给其他站长、给客户开授权」的发卡侧系统，那属于另一个独立的授权中心，不在本站插件范围内（可复用同一套授权表结构，但入口在服务端）。

01 · 为什么是插件而不是主题页

现在的能力散在 pay-admin.php（498 行、裸表格、无筛选无分页无审计），且主题升级会覆盖它。抽成 Typecho 插件后：主题可换、控制台不动；插件可单独发版；数据表与主题无关；访问走独立路由并做管理员鉴权。

usr/plugins/EcodConsole/
├── Plugin.php              # activate() 建表 / 注册路由 / 后台菜单挂入口
├── Action.php              # 路由控制：GET 渲染页面，POST 分发动作
├── core/
│   ├── auth.php            # administrator 校验 + 令牌 + 同源 + 限流
│   ├── orders.php          # 列表/筛选/结算/关闭/批量/导出
│   ├── members.php         # 会员聚合、授予、延期、降级、撤销
│   ├── license.php         # 授权校验、心跳、换绑、模块开关
│   ├── ads.php             # 广告审核（复用主题表）
│   ├── tickets.php         # 工单队列 / 会话 / 状态 / 内部备注
│   ├── notices.php         # 站内信推送与发送记录
│   ├── tasks.php           # 任务奖励覆写、显隐、统计
│   └── audit.php           # 写操作留痕
├── views/
│   ├── layout.php  dashboard.php  orders.php  confirm.php
│   ├── members.php  tickets.php  notices.php  tasks.php
│   ├── license.php  ads.php  settings.php
└── assets/  console.css  console.js

02 · 信息架构

九个一级页，分四条线：交易主线「钱进来 → 确认 → 发权益 → 看留存」，用户服务线（工单 / 消息 / 任务），站点线（授权 / 广告），系统线。待确认与工单都独立成页，因为它们都是高频、连续、要看上下文再操作的核对型工作，塞进列表页会拖慢节奏。

运营
概览        今天该干什么：收入、待办、异常（含待处理工单）
订单管理    全量检索、筛选、批量、导出
待确认      核对凭证 → 确认收款 → 发权益（J/K 连续处理）
会员管理    谁在付费、什么时候到期、消费多少

用户
工单处理    看时间线 → 回复 → 关单；回复即推站内信（J/K 连续处理）
消息推送    全站公告 / 定向 / 分群，写 ecod_notifs，可查触达与已读
任务配置    10 项任务的奖励、上限、显隐；改完即时生效

站点
主题授权    这张票还能用多久、能开哪些功能、要不要更新
广告位      投放审核与上线

系统
设置        确认规则、通知、入口路径、审计与导出
设计规格    本页

03 · 数据模型

订单、权益、卡密、广告全部复用主题现有表，插件只新增三张表，避免两套账。工单、消息、任务同理全部落在主题表里（前台要读，插件不能独占），插件只是这批表的第二个写入口：插件禁用后数据仍在、前台仍可看，只是没人处理。

复用
typecho_ecod_orders         订单主表（order_no 唯一）
typecho_ecod_entitlements   权益（vip / post，expire_at=0 永久）
typecho_ecod_pay_cards      卡密（只存 SHA-256）
typecho_ecod_ads            广告投放

复用 · 用户侧
typecho_ecod_notifs         站内消息（uid/type/title/body/link/is_read）
                            # 消息推送写这里；type 需含 notice / ticket
typecho_ecod_credits        积分流水（任务发奖 type='task'，ref=任务 key）
typecho_ecod_tickets        工单主表（no 唯一 / status / priority / last_side / unread_*）
typecho_ecod_ticket_msgs    工单会话（side=user|staff，纯文本）
typecho_ecod_task_claims    任务领取（uid+task+period 唯一，幂等闸门）
                            # 奖励数值不进表，覆写在插件 option 里

新增
ecod_console_proof     id, order_no, image, note, uid, created
                       # 收款凭证；一单可多图，取最新为展示主图
ecod_console_license   id, lic_key, domain, fingerprint, edition,
                       modules(json), issued_at, expire_at, last_ping, status
ecod_console_audit     id, uid, action, target, payload(json), ip, ua, created
                       # 所有写操作必写一条；保留 180 天

04 · 路由与动作

单一入口 /console，页面用 ?p= 区分，写操作用 POST + 动作名，全部走令牌与同源校验。结算必须幂等：以 order_no 唯一定位、事务内校验 status='pending'，重复确认直接返回「已结算」而非报错。工单回复同理：先写 ticket_msgs 再更新主表 msgs/updated/last_side/unread_user，同一 body 60 秒内重复提交只落一条。

GET  /console?p=dashboard|orders|confirm|members
                |tickets|notices|tasks|license|ads|settings
POST /console
  action=order.settle      order_no
  action=order.close       order_no
  action=order.refund      order_no, note      # 只标记，不调通道退款
  action=order.bulk        order_nos[], op
  action=member.grant      uid|name, kind, level, days
  action=member.extend     uid, days
  action=member.revoke     uid, kind, target
  action=ticket.reply      tid, body, close?    # 写入 ticket_msgs(side=staff)
  action=ticket.status     tid, status          # open|resolved|closed
  action=ticket.priority   tid, priority
  action=ticket.note       tid, body            # 内部备注，side=note，用户不可见
  action=notice.send       scope, uid|group, title, body, link, at?
  action=notice.delete     id                  # 撤回整行，用户侧同步消失
  action=task.reward       key, reward, cap?
  action=task.toggle       key, on
  action=license.bind      lic_key, domain
  action=license.ping
  action=license.module    key, on
  action=export            type=csv

05 · 安全约定

鉴权     Typecho 登录态 + group=administrator，双保险
令牌     账户令牌（ecod_account_token），所有写操作校验
同源     Origin/Referer 必须为本站；拒绝跨站表单
限流     结算 20 次/分、导出 3 次/分，超限 429
幂等     结算以 order_no 为键，事务内二次校验状态
审计     写操作记录 uid/动作/目标/IP/UA，可导出
敏感     凭证图不落公开目录，走带鉴权的读取入口
降级     授权心跳失败只提示、不锁站（宽限 7 天）
工单     正文纯文本入库、输出转义；单条 ≤2000 字，回复 30s 1 条
推送     标题 ≤60 字、正文 ≤500 字；群发 3 次/分，超限 429
可见性   ticket.note（内部备注）只在控制台渲染，前台 API 永不下发

06 · 交互规范

沿用主题的 4pt 网格与墨色三档，控制台只增加密度，不引入新色。数字全部等宽（tabular-nums），状态只用「色点 + 文案」，不靠颜色单独传达信息。

间距     4 / 8 / 12 / 16 / 24，禁止 5、10、18
圆角     卡面 12、控件 8、微元素 6，胶囊仅用于标签
主色     #4f6ef2 只用于主操作与选中态，一屏不超过 2 处实心
状态     待确认=琥珀、已支付=绿、已退款=红、已关闭=灰
密度     表格行高 52，页面边距 24/28，卡内 18
键盘     待确认页 J/K 切换、Enter 确认；工单页 J/K 切换、⌘↵ 发送、Esc 关抽屉
反馈     写操作 1 秒内出结果，成功用轻提示，失败给原因

07 · 交付验收

插件启用后自动建表，禁用不删数据activate / deactivate 幂等
非管理员访问 /console 返回 403 且不泄露数据不渲染任何订单字段
待确认页可连续处理 10 笔订单，键盘不离开列表J/K/Enter 全链路
同一订单重复确认不会重复发权益事务 + status 二次校验
广告订单确认后自动进入广告待审队列不直接上线
会员延期、降级、撤销后前台权益立即变化读同一张 entitlements
授权到期 30 天内在展开提示，不影响交易心跳失败宽限 7 天
所有写操作可在审计页查到含失败操作
工单回复后用户侧「消息中心」出现一条，tab 角标 +1reply/notice 同一套未读计数
内部备注不出现在任何前台接口返回里ticket_detail 只回 side=user|staff
关闭工单后用户端回复框禁用、只能新建服务端同样拒绝向 closed 写入
群发触达数等于实际写入行数，删除后用户侧同步消失撤回=删行，不做软删
改任务奖励后前台 5 分钟内生效，已领记录与流水不变覆写配置、不动 claims
积分总开关（ECrOn）关闭时任务页全部置灰并提示不静默失败
390px 宽度可用，表格横向滚动而非挤压移动端只保留确认与查询

08 · 与主题侧的分工

控制台不复制前台逻辑，只对同一批表做第二个写入口。三处联动必须两侧字段对齐，否则会出现「后台改了、前台不认」；同时对「谁可以写哪一侧」有硬约束。

工单
主题 page-user.php  tab=ticket          # 读 ecod_tickets / ecod_ticket_msgs
主题 api.php        ticket_*            # 用户侧建单 / 回复 / 关闭（只写 side=user）
插件 tickets.php    ticket.reply        # 客服回复（只写 side=staff）+ 推站内信
插件 tickets.php    ticket.note         # 内部备注（side=note），前台查询显式过滤
约束  状态只有 open|resolved|closed；「已回复 / 待处理」由 last_side 派生，不存第四态
      回复顺序：先 ticket_msgs → 再更新 msgs / updated / last_side / unread_user

消息
主题 core/site/notifs.php               # ecod_notif_broadcast / list / unread / read
插件 notices.php    notice.send        # 直接调主题函数，不另建消息表
约束  type 白名单必须同时含 notice 与 ticket，否则插入被拒（theme notifs.php:139）

任务
主题 core/user/tasks.php                # 进度 COUNT + 领取 + ecod_credits_add
插件 tasks.php      task.reward         # 只写插件 option：key => [reward, cap, on]
约束  读侧优先取覆写值、无覆写回落常量表；插件禁用后前台照跑（默认奖励）
插件不是必需依赖：禁用插件后工单数据仍在、用户仍可查看自己提交的工单，只是没人回复；消息与任务完全不受影响。这是刻意的——控制台负责「处理效率」，不负责「功能存在」。
