结论摘要

先说判断：本项目的结构不缺（文章头 / 元信息 / 正文 / 标签 / 相关 / 互动 / 上下篇 / 评论 / 侧栏全都有）， 缺的是层级、节奏与克制。guaqi 的做法不是加东西，而是减装饰、加秩序。

核心问题

  • 无层级元信息 5 个等重胶囊并列，标题与正文比例 1.46 倍
  • 无节奏间距实测出现 4/5/6/7/8/9/10px 七种，无 4pt 网格
  • 无克制卡片描边 #e4e7ee 过重，浮层又叠双阴影
  • 无主角每个区块视觉权重相同，读者不知道先看哪

参考站手法

  • 极浅描边#f2f2f9 1px，卡片零阴影
  • 分组卡同义区块用负 margin 拼接成一整块
  • 三档字号16 / 14 / 12，阶跃即层级，不靠颜色
  • 单品牌色#4945FF 独占，正文纯黑 + 60% 黑

预期收益

  • 正文可读性：字号 15→16、行高 1.75、行宽 640~700
  • 信息层级：元信息拆主次两组，减少 3 枚胶囊
  • 模块辨识：统一 head + 三档密度，侧栏不再同质堆叠
  • 成本可控：纯 CSS + 模板局部改，不动数据层
一句话方向：把文章页从「一张大白卡 + 若干同样重的模块」改写为 「头 / 身 / 反馈 / 关联」四段式分组卡，用间距和字号建立层级，描边与阴影只保留一套最轻的。

1.2五条可迁移法则

L1

单品牌色 + 两级中性色

强调色只承担「可点 / 关键数字 / 状态」，正文用 100% 与 62% 两档墨色。第三档灰只用于「标注」而非「内容」。

本项目现状：主色 + 琥珀强调 + 三级灰，且 gray 被大量用于正文级信息 → 需要收敛。
L2

描边代替阴影

静态容器一律 1px 极浅描边、零阴影；阴影只给 popover / 抽屉 / 吸顶条。

现状：卡片 #e4e7ee 偏重，同时浮层用双阴影 → 同屏两套层次语言。
L3

4pt 网格 + 两档密度

间距只取 4 的倍数（4/8/12/16/20/24/32），内边距只给 compact 12 与 regular 16（大块 24）两档。

现状实测：4/5/6/7/8/9/10 七种间距并存，等效于没有刻度。
L4

同义区块拼接成组

头 + 正文 + 反馈同属「这篇文章」，用负 1px 边距共享边框，只保留外侧圆角；关联与评论另起新组。

现状：10 个模块各自独立成卡、各自 12px 圆角 → 页面像「卡片墙」。
L5

每屏一个视觉主角

文章页主角只有一个：标题（+ 封面）。其余元素从属于它——元信息降级、按钮弱化为 ghost、数据用 mono 小字。

现状：标题 22px 与 5 枚胶囊 + 橙色朗读条争抢注意力。
S

不可照搬的部分

参考站是 SaaS 内容站，正文以「更新日志 + 短段」为主；本站是长文博客，行高、段距、目录、脚注必须比它更宽松， 不能直接抄 1.5 行高与 658px 列宽。

结论：抄「秩序」而不抄「密度」。

2.1七条病灶（按影响排序）

已排除 · 「critical CSS 摊平媒体查询」经复核为探针误报

  • 复核2026-10-30 用 CDP 实时页重测：1440 视口下 h1 = 27px、.ecod_article padding = 30px 32px、正文 15px —— 与源码完全一致； critical 产物内 @media 包裹完好（此前「22px / 26 24」来自一次探针测量错误）。
  • 沉淀仍在 build/build.mjs 加了 花括号平衡断言（源码与关键 CSS 抽取各一次）——防「少写一个 }」把媒体查询后半段泄漏到顶层这类静默事故；本稿其余结论不受影响。

P1 · 元信息失去层级

  • 证据.ecod_article__meta > * 给每一项都套胶囊：边框 + 底片 + 4/11 内边距
  • 后果「1k 阅读」和「后端开发」和「9 评论」视觉等重，读者无法快速抓关键
  • 修法拆两组：主信息无边框一行（图标 + 文字，gap 12）；次信息 12px 墨三档；状态徽标保留胶囊

P1 · 标题与正文比例过近

  • 证据标题 22px vs 正文 15px = 1.47 倍；h2 22px 与标题同号
  • 后果h2 与文章标题分不清，正文起点没有「入口感」
  • 修法标题 27 / h2 22 / h3 18 / 正文 16，四档拉开；h2 距上 40、距下 12

P2 · 装饰性分隔线过量

  • 证据全文 dashed 虚线大量用于 widget 标题、列表项、动作条、版权卡
  • 后果虚线密集出现 → 噪声；与实线混用 → 语义不明
  • 修法实线只用于「分隔不同语义」；虚线只用于「同组内条目」。动作条不用线，用间距

P2 · 侧栏模块同质化

  • 证据关于本站 / 最新文章 / 最新评论 / 标签云 全是 .ecod_widget：同 padding、同虚线头
  • 后果侧栏成「四张一样的白卡」，模块难辨识
  • 修法统一 head 加图标块；列表项统一 3 行结构（标题/摘要/元）；首屏模块用 loose 密度

P3 · 正文元素规格不齐

  • 证据h2/h3/h4 各用一套标记（竖条 / 短竖条 / 圆点）；图片无 figure/caption；表格恒横滚
  • 后果三种标题装饰互相打架，长文越读越乱
  • 修法标题只保留 h2 一根竖条，h3/h4 靠字号与留白；补 figure + figcaption 规范

P3 · 交互态缺失

  • 证据多数按钮只有 :hover 变色，无 :active 位移、无 :focus-visible 环
  • 后果键盘用户无焦点提示；点击无反馈
  • 修法统一三态：hover 加深 / active 下沉 1px + scale .98 / focus-visible 2px 环

4.5分组卡（本稿最关键的机制）

同一语义组内：只有首卡有上圆角、末卡有下圆角，相邻边共享 1px（避免双线）
① 头卡 · 标题 + 作者
② 身卡 · 正文
③ 尾卡 · 标签 + 动作条
组与组之间：16px 间距，各自完整圆角
④ 关联卡（相关阅读 / 上下篇）

06

模块化设计

现状的问题不是「模块不够多」，而是模块没有统一的壳语言：每个模块自带一套头、一套间距、一套分隔线。 参考站的做法是——所有模块共用同一个 .container-box（12 圆角 + 1px 浅边 + 两档 padding）， 模块之间只有内容不同。这条要抄。

6.1一个模块的五个属性

属性取值作用
shell 壳plain / card / memberplain 插在正文里不画卡；card 独立成卡；member 属于某个分组卡
density 密度compact / regular / loosepad 12/16/24、gap 8/12/16，一套变量三档
head 头icon / plain / noneicon 带图标块（列表类）；plain 纯标题；none 无头（广告、通栏）
grid 列1 / 2 / 3 / auto由所在区域决定，模块自己不自适应乱变列
empty 空态hide / hint默认 hide（不渲染）；hint 只在后台预览时显示占位

6.2壳语言：一张表定全部

card · loose（文章内模块）
◆相关阅读全部
card · regular（侧栏模块）
◆热门文章
card · compact（数据/标签）
◆标签云
member（分组卡内）
组内成员：无独立圆角、无左右外边线

6.3模块头三型

icon 型（默认）

  • 结构图标块 22 + 标题 14/600 + 右侧 more
  • 图标13px 线性图标，语义化（榜单=奖杯、评论=气泡）
  • 下距12（regular）/ 8（compact）
  • 适用于热门、最新、评论、相关、排行榜

plain / none 型

  • plain只有标题（16/600），用于正文内的「延伸阅读」
  • none广告位、通栏 CTA、订阅框，不加头避免抢注意力
  • 禁用同一卡里出现两种头型（既有图标头又有加粗小标题）
